# Database

PostgreSQL 13 or later through TypeORM. Entities live flat in `src/entities/` because several are referenced from more than one module. Column names are `snake_case` via `SnakeNamingStrategy`; primary keys are `uuid` generated by `gen_random_uuid()` (built in from PostgreSQL 13, no extension required).

## Relationships

```
User 1──* Session
User 1──* OtpCode
User 1──* Shipment        (as sender)
User 1──1 Wallet
Wallet 1──* WalletTransaction
```

## Tables

### `users`
Identity and role. `email` (stored lower case) and `phone` are unique. `role` defaults to `user`; there is no code path that assigns another role, so privilege escalation through the API is not possible. Seeded staff, manager and admin accounts are created by the seed script only. `is_active` allows suspension. `password_hash` is excluded from serialisation.

### `sessions`
`id` is the SHA-256 of the session token, not the token. `revoked_at` marks a session invalid while keeping the row as history. Index on `user_id` supports `revokeAllForUser`.

### `otp_codes`
`code_hash` is an HMAC of the code. `attempts` is incremented atomically. `consumed_at` marks use or supersession. `purpose` is `signup_verify` or `password_reset` — a Postgres enum, extended by a migration when this list grows. Index on `(user_id, purpose)` matches the only lookup: latest unconsumed code for a user and purpose, and the two purposes are tracked (and cooled down) independently for the same user.

### `shipments`
The dashboard's core entity.

| Column | Notes |
|---|---|
| `tracking_id` | Unique, format `MAF-###-###-###` |
| `sender_id` | Owner; basis for ownership rules |
| `receiver_name`, `pickup_location`, `delivery_location` | Display values |
| `type` | `export`, `import`, `domestic`, drives the KPI cards |
| `status` | `pending`, `in_transit`, `delayed`, `delivered`, `cancelled` |
| `payment_status` | `unpaid`, `paid` |
| `amount` | `numeric(12,2)` |
| `processing_time_hours` | Shown as "Processing time" |

Indexes:

- `(sender_id, created_at)` serves every customer query: scope filter plus a date range or ordering, in one index scan.
- `(status)` serves company-wide status filters, where there is no `sender_id` predicate to use the composite.
- `tracking_id` is covered by its unique constraint.

Further indexes were deliberately not added: each one slows every insert and update, and no current query needs them.

### `wallets`
One per user, created lazily on first access with `INSERT ... ON CONFLICT DO NOTHING` so concurrent first requests cannot create duplicates. A `CHECK (balance >= 0)` constraint makes an overdraft impossible even if application code is wrong.

### `wallet_transactions`
Append-only ledger of credits and debits. `reference` is unique, which provides idempotency:

- Funding: the client supplies the reference. A repeat with the same amount returns the original result (`replayed: true`); the same reference with a different amount is `409`.
- Shipment payment: the reference is `SHIPMENT_PAYMENT:<shipmentId>`, so one shipment can be paid at most once at the ledger level too. Client references cannot contain `:` and therefore cannot collide with it.

Index on `wallet_id` supports history listing.

## Money

Amounts are `numeric` columns, typed as `string` in TypeScript. `pg` returns `numeric` as a string to avoid float rounding, and the API passes strings through unchanged. Where the code must compare amounts (funding limits, replay detection) it converts to integer minor units with `BigInt`, never `Number`. Balance changes are done in SQL (`balance = balance - :amount WHERE balance >= :amount`), not read-modify-write in JavaScript.

Currency is NGN throughout; there is no multi-currency support.

## Transactions and concurrency

Paying a shipment runs in one transaction:

1. `SELECT ... FOR UPDATE` on the shipment row, which serialises concurrent payments of the same shipment.
2. Reject if already paid or cancelled.
3. Conditional balance decrement; zero rows affected means insufficient funds.
4. Insert the ledger row.
5. Mark the shipment paid.

Verified with five simultaneous pay requests: one `200`, four `409`, balance debited exactly once. Four simultaneous fundings with one reference credit exactly once.

## Dates

Timestamps are `timestamptz`. Dashboard periods and chart buckets use UTC calendar boundaries. Using a business timezone (for example `Africa/Lagos`) would be a change to `date-range.util.ts` and the `date_trunc` expression only.

## Migrations

`synchronize` is off in every environment. Schema changes go through migrations.

```bash
pnpm migration:generate src/database/migrations/AddSomething
pnpm migration:run
pnpm migration:revert
```

The initial schema is committed in `src/database/migrations/`. Review generated SQL before committing it.

## Seed data

`pnpm seed` creates five users, two customer wallets and about 350 shipments across the current year with a deterministic pseudo-random generator, so every run produces the same shape. It refuses to run when `NODE_ENV=production` and requires `SEED_PASSWORD`. It is a no-op if the seed users already exist. The customer `user@securebypay.test` also has the two shipments from the design (`MAF-100-234-291` in transit and paid, `MAF-100-234-292` delayed and unpaid).
